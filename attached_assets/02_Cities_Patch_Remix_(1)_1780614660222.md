## 1. What this patch delivers (Cities surface)

1. **Per-tenant contact identity on city pages** — the email + phone shown on each
   `city_locations`-driven page resolves from the tenant's persona config, not a global constant.
2. **Optional author/publisher stamping** on `city_locations` rows (or the tenant table),
   scoped per tenant — so a city page can attribute content to that tenant's persona.
3. **A safe, atomic, per-tenant rollup** to backfill contact/author values where missing —
   that **never** blindly overwrites curated data.
4. **Per-tenant brand in city meta descriptions** — the tenant's brand named once, in the closing sentence (see §6).

## 3. The hard rules (this is where the origin patch is dangerous)

1. **Never blanket-overwrite curated contact data.** The origin rollup set *every*
   `city_locations.email`/`phone_number` to one global value across all tenants. For a
   multi-persona remix that is **destructive** — it erases per-tenant contacts. Scope every
   UPDATE to a single tenant and only fill rows that are **missing or placeholder**, e.g.:
   ```sql
   UPDATE <tenant>.city_locations
   SET email = $1, phone_number = $2
   WHERE (email IS NULL OR email = '' OR lower(email) NOT LIKE '%@' || $3)
   -- $1=tenant email, $2=tenant phone, $3=tenant domain
   ```
   Cities already on the tenant's canonical domain are untouched → re-running is a no-op.
2. **One tenant per run, per persona value.** Loop tenants only with each tenant's OWN
   email/phone/author — never one global constant across the loop.
3. **Atomic + dry-run first.** Wrap in a single transaction. Default to dry-run (print the
   row counts that WOULD change), require an explicit `--confirm` to commit.
4. **Forward-only, but reversible.** Take a DB snapshot before committing. Do not ship a
   "reset to NULL" script.

## 4. Rollup skeleton (adapt to the confirmed tenancy model)

```typescript
// scripts/cities-contact-rollup.ts  (REMIX — per-tenant, missing-only)
import { Pool } from "pg";

// Each tenant carries its OWN persona contact. NEVER one global value.
const TENANTS: Record<string, { email: string; phone: string; domain: string }> = {
  // "acme":   { email: "info@acme.com",   phone: "(800) 000-0000", domain: "acme.com" },
  // "globex": { email: "info@globex.com", phone: "(800) 111-1111", domain: "globex.com" },
};

const confirm = process.argv.includes("--confirm");
const pool = new Pool({ connectionString: process.env.PROD_DATABASE_URL });

async function main() {
  const c = await pool.connect();
  let total = 0;
  try {
    await c.query("BEGIN");
    for (const [slug, t] of Object.entries(TENANTS)) {
      // schema-per-tenant shown; for row-level use: ...city_locations WHERE tenant_id=$4
      const res = await c.query(
        `UPDATE tenant_${slug}.city_locations
            SET email = $1, phone_number = $2
          WHERE email IS NULL OR email = '' OR lower(email) NOT LIKE '%@' || $3`,
        [t.email, t.phone, t.domain]
      );
      console.log(`  [${slug}] cities filled: ${res.rowCount}`);
      total += res.rowCount ?? 0;
    }
    if (confirm) { await c.query("COMMIT"); console.log(`✅ committed ${total}`); }
    else { await c.query("ROLLBACK"); console.log(`🧪 dry-run, would change ${total}`); }
  } catch (e) { await c.query("ROLLBACK"); console.error("❌ rollback", e); process.exit(1); }
  finally { c.release(); await pool.end(); }
}
main();
```

## 6. Brand in city meta descriptions (per tenant)

City landing pages also carry an SEO meta description that **names the brand once, in the
closing sentence**, value-first and grounded in the page's narrative — verified live on the
origin (every sampled prod city resolves to a single closing-sentence brand mention). This
is produced by the city meta generator, a concern **separate** from the contact identity in
§§1–5, and the origin bakes the brand in as a global `BRAND_NAME` constant.

The same multi-persona rule applies: **resolve the brand per tenant** from the tenant's
brand/persona config — never a global constant, and build any brand-presence regex from the
resolved value. See **Pearl 3 §6** for the exact rule, the lightweight retry gate (brand
exactly once, in the last sentence — not presence-only), and the chunked per-tenant backfill
discipline; apply it identically to the cities surface.
